# L4.1 · A/B test design and hygiene

<p class="lesson-meta">Day 4 · Part B · Basic → Advanced 75 min · Leader 35 min · Prerequisites: L3.4, L3.6 · Recipe: <code>rcp_ab_test</code></p>

<div class="you-are-here">📍 <b>You are here:</b> Compare groups (is A different from B?) › Yes — randomised test, not yet checked › <a href="../../navigator/#N-EXP-SRM">Sample-ratio-mismatch check (chi-square on assignment counts)</a> <code>N-EXP-SRM</code></div>

**Objectives** — you can: design a test (unit of randomisation, primary / secondary / guardrail metrics, duration, sample size);
check sample-ratio mismatch (SRM) before reading any result and localise its cause; recognise novelty, primacy and interference;
and decide when a test result can be trusted at all.

## 1. Business question

=== "Retail"

    > "Did the new e-coupon raise 14-day conversion in the app?"

=== "Finance"

    > "Design the test for a new credit-card balance-transfer offer."

## 2. Concept

=== "Basic → Advanced"

    ### 2.1 The design checklist

    | Decision | E-coupon (retail) | Card offer (finance) |
    | --- | --- | --- |
    | Unit of randomisation | app user | customer (not account — one customer, one offer) |
    | Primary metric | converted within 14 days | offer take-up within 30 days |
    | Secondary | revenue in 14 days | balance transferred |
    | Guardrails | revenue must not fall | 90-day delinquency, complaints, margin |
    | Planned split | 50/50 | 50/50, stratified by risk band |
    | Sample size | from `rcp_power` (L3.6) | +1 pp on a 6% base: **9,527 per arm** |
    | Duration | ≥ 2 full weeks (weekly cycles) | ≥ one statement cycle + 30 days |
    | Analysis plan | pre-registered (L3.7) | pre-registered |

    ### 2.2 Hygiene check 1 — sample-ratio mismatch

    The test was planned 50/50. Logged: **6,000 treatment vs 5,421 control** (52.5% treatment).
    A chi-square test against 50/50 gives χ² = 29.4, **p = 6e-08**. With true 50/50 randomisation a gap
    this large essentially never happens. Something removed or added users non-randomly — **stop and diagnose before reading the
    effect**.

    **Localise it.** Repeat the check within segments:

    | Segment | Treatment | Control | p |
    | --- | --- | --- | --- |
    | app 3.1 | 1,742 | 1,781 | 0.51 |
    | app 3.2 | 2,388 | 1,820 | 2e-18 |
    | app 3.3 | 1,870 | 1,820 | 0.41 |
    | platform android / ios | — | — | 6.9e-05 / 0.00023 |

    The mismatch lives in **app version 3.2** (both platforms are affected only because 3.2 runs on both). In 3.2 the control arm
    shows 13.0% conversion against 11.1% for treatment — control users who *did not* convert went
    missing from the log on that version, inflating control's conversion.

    ### 2.3 What the broken test says — and what it hides

    | Reading | Treatment | Control | Lift | 95% CI | p |
    | --- | --- | --- | --- | --- | --- |
    | As logged (SRM) | 11.5% | 11.07% | 0.43 pp | -0.73 to 1.59 | 0.466 |
    | Excluding app 3.2 (SRM gone, p = 0.897) | 11.79% | 10.08% | **1.71 pp** | 0.27 to 3.15 | 0.0197 |

    The logging bug hid a real lift (the planted true effect is +1.5 pp — inside the clean CI). Excluding 3.2 is a
    **sensitivity analysis**: it assumes 3.2 users respond like the others. The proper fix is to repair logging and re-run (or recover
    the missing users from the assignment service).

    ### 2.4 Hygiene check 2 — balance and A/A

    Pre-period 30-day spend does not differ by arm in the clean data (p = 0.714). Platforms should run regular A/A
    tests (L3.3): ~5% "significant", SRM rarely.

    ### 2.5 Threats that a clean SRM does not rule out

    | Threat | What happens | Defence |
    | --- | --- | --- |
    | Novelty effect | users try the new thing, then revert | run ≥ 2 weeks; plot effect by week of exposure |
    | Primacy effect | users resist change at first | same |
    | Interference | treated users affect control (shared stock, social, marketplace) | cluster randomisation (stores, regions) |
    | Contamination | control users see the offer (shared devices, staff) | assign at the right level; measure exposure |
    | Seasonality | test window unrepresentative | avoid holidays or include full cycles |

=== "Leader"

    !!! abstract "Refresh"
        Design before data: unit, metrics, guardrails, size, duration, analysis plan. Read nothing until the SRM check passes.
        An SRM means a broken experiment, not an interesting result.

    **Judgement points**

    - **Make SRM a hard gate.** The e-coupon readout as logged said "no effect" (p = 0.466); the real effect was about
      +1.71 pp. A broken pipeline almost killed a winning idea.
    - **Guardrails are the leader's metrics.** Juniors optimise the primary metric; you protect margin, risk and customers.
    - **The unit of randomisation is a business decision.** Store-level tests avoid interference but have few units (L3.6); user-level
      tests have power but may contaminate.

    !!! tip "Coaching card"
        First question on any readout: *"What was the planned split and what did we observe?"* Second: *"Which guardrails moved?"*

| Section | Read as |
| --- | --- |
| **Decision** line | STOP on SRM; otherwise ship / caution / don't ship / inconclusive vs the practical threshold |
| 1. Sample-ratio check | planned vs observed; segment table; *localised in* line |
| 2. Primary metric | unadjusted and CUPED rows with CI and p |
| 3. Bayesian reading | P(treatment better), credible interval, expected loss (L4.3) |
| 4. Guardrails | breach = CI entirely on the bad side |
| looks.png | cumulative p-values by day — descriptive only (L4.2) |

## 6. Scenario matrix

=== "Basic → Advanced"

    | Check | Fails → |
    | --- | --- |
    | SRM overall | stop; localise by segment, date, platform |
    | SRM only in one segment | logging/eligibility bug there; sensitivity analysis + fix |
    | Pre-period imbalance (p small) | check randomisation; use CUPED/ANCOVA |
    | Effect fades week by week | novelty; extend the test |
    | Control exposed to treatment | contamination; re-design unit |

=== "Leader"

    | Readout says | You say | Norm |
    | --- | --- | --- |
    | "52.5/47.5 is close enough to 50/50" | "p = 6e-08 — it's broken" | SRM gate at p < 0.001 |
    | "primary up, complaints up" | guardrail breach → don't ship | guardrails pre-agreed |
    | "ran 4 days, significant" | weekly cycle, novelty | ≥ 2 full weeks |

## 8. Exercises

### Retail · NorthStar

??? example "R4-1 · Basic · Sample-ratio check"
    **Business framing:** The product team sends the e-coupon results and asks for a verdict.

    **Deliverable:** Run `retail_ecoupon_ab.yaml`: planned vs observed split, χ² p, and the decision line.

    ??? success "Expected finding and model answer"
        **Expected:** 6,000 vs 5,421 (52.5% treatment); p = 6e-08; decision STOP. *(tolerance: exact counts)*

        **Model answer:** A 52.5/47.5 split on 11,400 users is far outside chance for a 50/50 design. The experiment is broken; no effect estimate can be trusted yet.

        **Common wrong answer:** Reading the conversion lift first.

    **Leader drill:** Who should be told, and what should they do first?

??? example "R4-2 · Applied · Localise the SRM"
    **Business framing:** Engineering asks where to look.

    **Deliverable:** SRM check by app version and platform; conversion by arm within the failing segment; most likely mechanism.

    ??? success "Expected finding and model answer"
        **Expected:** Only app 3.2 fails (p = 2e-18); 3.1 and 3.3 pass. In 3.2 control converts at 13.0% vs 11.1% treatment. *(tolerance: ± 0.2 pp)*

        **Model answer:** Control users on 3.2 are missing, and the missing ones are non-converters (control's conversion is inflated). Likely a logging event that only fires for control users after a conversion on 3.2.

        **Common wrong answer:** Blaming platforms — both fail only because 3.2 runs on both.

    **Leader drill:** What monitoring would have caught this on day one?

??? example "R4-3 · Stretch · Sensitivity reading without 3.2"
    **Business framing:** The product owner wants a provisional answer while logging is fixed.

    **Deliverable:** Run `retail_ecoupon_ab_excl_v32.yaml`; report SRM, lift with CI, p, guardrail (revenue), and caveats.

    ??? success "Expected finding and model answer"
        **Expected:** SRM p = 0.897; lift 1.71 pp (CI 0.27 to 3.15), p = 0.0197; revenue per user 4.68 vs 3.85. *(tolerance: ± 0.05 pp)*

        **Model answer:** Provisionally the coupon raises conversion by ~1.7 pp — the logged result (+0.4 pp, n.s.) was an artefact. Caveat: assumes 3.2 users behave like others; re-run after the fix.

        **Common wrong answer:** Reporting the sensitivity result as final.

    **Leader drill:** Would you allow a launch on the sensitivity result? Under what conditions?

### Finance · Meridian

??? example "F4-1 · Basic · Design the card-offer test"
    **Business framing:** Marketing wants to test a balance-transfer offer.

    **Deliverable:** Unit of randomisation, primary/secondary/guardrail metrics, split, stratification, sample size for +1 pp on a 6% take-up, duration.

    ??? success "Expected finding and model answer"
        **Expected:** Customer-level randomisation; primary take-up within 30 days; guardrails 90-day delinquency and complaints; stratify by risk band; 9,527 customers per arm. *(tolerance: n ± 2%)*

        **Model answer:** Randomise customers (not accounts) to avoid one customer receiving both; stratify by risk band so arms are balanced on what drives delinquency; run past one statement cycle so delinquency guardrails can be observed.

        **Common wrong answer:** Randomising accounts, or omitting risk guardrails.

    **Leader drill:** Which guardrail would you give veto power, and at what threshold?

??? example "F4-2 · Applied · SRM check for champion/challenger"
    **Business framing:** Before reading the collections results, check the split.

    **Deliverable:** Run `finance_challenger_ab.yaml`: planned 80/20 vs observed; p; segment SRM table.

    ??? success "Expected finding and model answer"
        **Expected:** Challenger share 20.5% vs 20% planned; p = 0.418; no segment below p = 0.001. *(tolerance: ± 0.1 pp)*

        **Model answer:** The split is consistent with the plan. Region R4's small p (~0.04) is one of six segment checks — not alarming (multiple testing).

        **Common wrong answer:** Testing against 50/50.

    **Leader drill:** Which SRM threshold would you set for segment checks, and why?

??? example "F4-3 · Stretch · Interference in collections"
    **Business framing:** Collections agents handle both champion and challenger accounts.

    **Deliverable:** Describe how agents could contaminate the test and propose a design that avoids it.

    ??? success "Expected finding and model answer"
        **Expected:** Agents may carry challenger techniques into champion calls (contamination), biasing the difference toward zero; randomise agents (teams) instead, or train only a dedicated challenger team. *(tolerance: —)*

        **Model answer:** Cluster randomisation at team level removes contamination at the cost of fewer units — size it with a design effect (L3.6).

        **Common wrong answer:** Ignoring contamination because accounts were randomised.

    **Leader drill:** Would a team-level test be feasible with your number of teams?
