## 2. Concept

=== "Basic → Advanced"

    ### 2.1 Six dimensions of data quality

    | Dimension | Question | Example check |
    | --- | --- | --- |
    | **Completeness** | Is everything there? | null rates, expected row counts |
    | **Validity** | Do values obey the rules? | age 18–100; quantity < 0 only for returns |
    | **Accuracy** | Do values match reality? | revenue = quantity × unit price; reconcile to finance |
    | **Consistency** | Do related fields agree? | `promo_flag` true ⇔ `discount_pct` > 0 |
    | **Uniqueness** | No unintended duplicates? | `line_id` unique |
    | **Timeliness** | Is it current and in the right period? | max date vs expected; no future dates |

    ### 2.2 Write rules, then count — do not delete

    A **rule** is a condition that is *true for bad rows*. Write it in the config, give it a severity and a reason, and let the
    recipe count the rows it affects:

    ```yaml
    - {name: negative_qty_not_return, flag: "(quantity < 0) & (return_flag == False)", severity: error,
       why: "Sales lines cannot have negative quantity; returns are flagged separately"}
    ```

    | Severity | Meaning | Default treatment |
    | --- | --- | --- |
    | **error** | Impossible under business rules | Quarantine; ask the data owner; exclude from analysis with a note |
    | **warning** | Possible but suspicious | Investigate; keep with a flag until explained |

    ### 2.3 Duplicates

    *Exact duplicate rows* (every column identical) usually mean a file was loaded twice. *Duplicate keys with different values*
    mean conflicting records — never keep "the first" without understanding why. In the retail panel **150** lines
    appear twice.

    ### 2.4 Unit and scale errors

    A price typed as 1250 instead of 12.50, a discount stored as 0.25 instead of 25, amounts in cents instead of units. Detect
    them by comparing with a reference (list price), by impossible ratios, and by **where and when** they occur — a scale error
    often starts on a specific date or in one channel (here: online discounts from week 80, R19).

    ### 2.5 Reconciliation

    Compare totals to an independent source with a known scope. The panel is a *customer sample*, so it will not match chain
    sales — reconcile what should match (stores, weeks, trends), and explain what should not.

=== "Leader"

    !!! abstract "Refresh"
        Six dimensions (completeness, validity, accuracy, consistency, uniqueness, timeliness). Rules flag; people decide.
        Quarantine, never silently delete. Quantify each issue's impact on the business number.

    **What changes when you are accountable**

    - **Impact, not counts.** "25 decimal-shift lines" sounds trivial; "revenue overstated by
      10.3%" does not. Ask juniors to express every issue in the unit of the decision.
    - **Rules encode business knowledge.** A first-draft rule "unit price above list price" flagged a third of all lines — because
      regional shelf prices legitimately sit above list. A rule that flags a third of the data is a misunderstanding, not a finding.
      Rules must be reviewed with the business.
    - **Concentration is a signal.** An accuracy rule firing in **one store only** (233 of
      233 mismatches) points to a process or integrity problem, not random noise.
    - **Fix at source.** A cleaning step in an analysis notebook fixes one analysis; a ticket to the data owner fixes all of them.

    !!! tip "Coaching card"
        When a junior reports "I cleaned the data", ask for the issue log: rule, severity, rows, treatment, who was told. No log,
        no cleaning — just deletion.

## 3. When to use, assumptions, fallbacks

| | |
| --- | --- |
| **Use** | Before any analysis on a new extract, and on every refresh |
| **Assumes** | Rules reflect how the business actually works (validate with the owner) |
| **If unsure whether a value is an error** | Keep it, flag it, run the analysis with and without it |
| **Do not** | Delete rows to make a chart look clean; fix values by guessing |

## 6. Scenario matrix

=== "Basic → Advanced"

    | Pattern | Meaning | Next step |
    | --- | --- | --- |
    | Rule flags < 1% | Isolated errors | Quarantine, document, continue |
    | Rule flags > 10% | Rule probably wrong | Re-check the business definition |
    | Issue starts on a date | Pipeline or process change | Compare before/after; tell the data owner |
    | Issue in one store/branch | Local process or integrity problem | Escalate; check other fields for the same unit |

=== "Leader"

    | Pattern | Likely causes | Action — why / when / when not | Norm (rule of thumb) |
    | --- | --- | --- | --- |
    | Small share of hard errors | Entry errors | Quarantine + source ticket; proceed with a methods note | Report any issue moving a KPI > 1% |
    | Scale change from a date | System upgrade, new feed | **Freeze affected KPIs** until fixed; do not "patch" silently in one report | Monitor field distributions after every release |
    | Accuracy errors in one unit | Manual overrides, fabrication | Escalate to audit with evidence (Day 2 Benford) — not to the store first | Segregation of duties |
    | Duplicates after a load | Re-run without idempotency | Fix the load; de-duplicate on the key with a log | Loads must be idempotent |

## 9. Exercises

### Retail · NorthStar

??? example "R1-3 · Basic · Run the data-quality recipe"
    **Business framing:** Produce the issue log before any analysis.

    **Deliverable:** Run `retail_quality_transactions.yaml`. Rows flagged per rule; duplicates.

    ??? success "Expected finding and model answer"
        **Expected:** Duplicated ids 150; negative qty on non-return lines 40; price > 20× list 25; revenue ≠ qty × price 233 (unique lines); discount stored as a fraction 262. *(tolerance: exact)*

        **Model answer:** Each rule is a question for the data owner. Errors (negative non-return quantities, decimal shifts) are quarantined; warnings (revenue mismatch, fractional discounts) need investigation — both turn out to be planted issues.

        **Common wrong answer:** Deleting all flagged rows, including warnings, without investigation.

    **Leader drill:** Classify each finding as error, investigate, or acceptable — and say who you would ask.

??? example "R1-4 · Applied · How much do the errors inflate revenue?"
    **Business framing:** Finance asks how wrong a naive revenue total would be.

    **Deliverable:** Sales revenue total raw vs after removing duplicates, negative non-return lines and decimal-shift lines.

    ??? success "Expected finding and model answer"
        **Expected:** Raw 176,207 vs clean 159,780: raw overstates by 10.3%. *(tolerance: ± 0.2 pp)*

        **Model answer:** A handful of decimal-shift lines and 150 duplicates move the total by about a tenth — far more than most business effects you will later try to measure.

        **Common wrong answer:** Assuming errors 'average out'.

    **Leader drill:** How would you present this to the CFO without undermining trust in all analytics?

??? example "R1-5 · Stretch · A rule that only fires in one store"
    **Business framing:** Look at where `revenue ≠ quantity × unit_price` occurs.

    **Deliverable:** Count of mismatched lines overall and in the store with most mismatches; hypothesis.

    ??? success "Expected finding and model answer"
        **Expected:** 233 mismatched lines, 233 of them in S033. *(tolerance: exact)*

        **Model answer:** An error concentrated in one store is not random entry noise — it points to a process problem or manipulation in that store. Day 2 (Benford) tests this formally (R18).

        **Common wrong answer:** Recomputing revenue from qty × price everywhere and moving on.

    **Leader drill:** What would you ask the store-operations team before escalating?

### Finance · Meridian

??? example "F1-3 · Basic · Impossible values"
    **Business framing:** Validate customer attributes.

    **Deliverable:** Run `finance_quality_accounts.yaml`. Impossible ages, negative incomes, utilisation above 100%.

    ??? success "Expected finding and model answer"
        **Expected:** 12 impossible ages, 20 negative incomes, 35 accounts above 100% utilisation. *(tolerance: exact)*

        **Model answer:** Ages and negative incomes are errors (quarantine, ask the source). Over-limit utilisation can be genuine (fees, interest) — a warning, not an error.

        **Common wrong answer:** Treating every rule hit as an error.

    **Leader drill:** Which of the three do you escalate to the data owner?

??? example "F1-4 · Applied · Error or real? Over-limit cards"
    **Business framing:** Some cards show utilisation above 1.

    **Deliverable:** Default rate of over-limit cards vs others; decision.

    ??? success "Expected finding and model answer"
        **Expected:** 35 accounts; default 34.3% vs 3.7% for other cards. *(tolerance: —)*

        **Model answer:** If over-limit accounts default far more, the field is informative and almost certainly genuine. Validity rules must reflect how the business works, not a textbook range.

        **Common wrong answer:** Capping utilisation at 1 and losing a risk signal.

    **Leader drill:** Who should define validity rules — data teams or the business?
