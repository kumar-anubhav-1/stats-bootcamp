## 1. Business question

> "We did a great analysis last quarter. **Can we re-run it on new data — or another team's file — without rebuilding it and without breaking it?**"

## 2. Concept

=== "Basic → Advanced"

    A **recipe** is a tested, documented analysis (e.g. "profile a table", "compare two groups"). It never mentions your column
    names. Instead it asks for **roles** — `id`, `date`, `target`, `group`, `cluster`. A **config** file maps roles to the columns of
    a specific dataset:

    ```yaml
    recipe: rcp_profile
    dataset:
      name: northstar_transactions
      path: data/retail/transactions.parquet
    columns:          # role: column in THIS dataset
      id: line_id
      date: date
      target: revenue
    filters: []       # optional row filters, in the dataset's own column names
    params: {}        # recipe options
    ```

    To reuse the recipe on the bank data you change **only** `dataset` and `columns` — never the recipe code.

    **Every run writes a dated folder** in `outputs/` containing `narrative.md` (plain-English summary), result tables and
    plots, `schema_report.md` (did the data fit the recipe?), `row_accounting.md` (every row removed and why), `metrics.json`
    and `run_manifest.json` (config, data fingerprint, library versions).

    **Regression check.** After changing anything, re-run the *original* config with `--check-baseline`: the toolkit compares every
    number with the saved baseline and lists any that moved. Unchanged numbers prove you did not break the original analysis.

    **Schema check.** If a config maps a role to a column that does not exist, nothing is analysed; you get a plain message with
    likely matches (e.g. "`quantity` not found — possible match: `units_sold`").

=== "Leader"

    **Refresh:** recipes = parameterised, tested analyses driven by config; reuse by config only; regression check after every change.

    **Approval checklist for a reused analysis** (use it in the daily review huddle):

    - [ ] Schema report has **no errors**; warnings are explained.
    - [ ] **Grain** of the new data matches the question (store-week vs line vs customer).
    - [ ] **Units** checked (currency, cents vs units, grams vs kg).
    - [ ] **Row accounting** shown; any drop > 1% explained.
    - [ ] Parameters not **stale** (dates, filters, thresholds copied from the old project).
    - [ ] **Assumptions re-checked** on the new data — they do not transfer automatically.
    - [ ] **Regression check passed** on the original data after any code change.
    - [ ] Conclusion stated with **effect size and uncertainty**.

    !!! tip "Coaching card"
        When a junior says "I reused last quarter's script", ask: *"Show me the schema report and the row accounting for the new
        file."* If they cannot, the analysis is not reviewed yet.

## 4. Reuse drill — the renamed variant

`data/retail/variants/transactions_renamed.parquet` is the same data with different column names (as another retailer might
send it). Ask Claude Code to run the **retail** profile config against it unchanged. It will fail the schema check — read the
message, then ask Claude Code to map the columns (`/map-columns`) and write `retail_profile_renamed.yaml`. Compare the two
narratives: the numbers must be identical.
