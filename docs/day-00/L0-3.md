## 3. Concept: what "validated" means

=== "Basic → Advanced"

    Validation is checking that the data is what you think it is **before** you analyse it. Seven checks:

    | # | Check | Question | Retail example |
    | --- | --- | --- | --- |
    | 1 | **Row count** | Do we have the expected number of rows? | 25,000 transaction lines |
    | 2 | **Schema** | Are all expected columns present with the right types? | 38 columns; `quantity` numeric |
    | 3 | **Grain and keys** | What does one row represent? Is the key unique? | One row per line; `line_id` *should* be unique |
    | 4 | **Coverage** | Does the date range and entity list match? | 2024-11-04 to 2026-11-01; 40 stores |
    | 5 | **Completeness** | Which fields have missing values, and how many? | `household_size` 17.9% missing |
    | 6 | **Validity** | Do values obey business rules? | Quantities negative only for returns? |
    | 7 | **Reconciliation** | Do totals match an independent source? | Panel revenue vs chain weekly tables (different scope — know why) |

    **Grain** is the single most important idea in this lesson. The same question gives different answers at different grains:
    "average basket value" needs one row per *basket*, but `transactions` has one row per *line*. Always ask Claude Code to state
    the grain before computing anything.

=== "Leader"

    **Refresh:** validation = row count, schema, grain/keys, coverage, completeness, validity, reconciliation. It is a gate, not a formality.

    **What to demand before signing off an extract:**

    - A **validation report** with all seven checks, numbers, and the rows affected by each issue.
    - **Explicit grain statement** for every table and every join (join explosions are the most expensive silent error in analytics).
    - **Reconciliation to an independent total** — and an explanation when scopes differ (here: the transaction file is a
      *customer panel*; the weekly tables are *full chain*).
    - **Issues logged, not fixed silently.** Day 1 decides treatment; Day 0 only finds and counts.

    !!! tip "Coaching card"
        Ask a junior: *"What does one row represent, and how do you know?"* If the answer is a column name rather than a
        business entity ("one row per line item on a till receipt"), coach them to restate it.

## 4. Prompt cards

<div class="prompt-card" markdown>

**Weak:** "check the data"

**Better:** "Validate the retail transactions table."

**Expert:** "Validate `data/retail/transactions.parquet` against its data dictionary. Before running, state the grain you

`line_id`, date range, number of stores/customers/SKUs, % missing per column, and any values that break business rules

**What to verify:** the row count is exactly 25,000; the report notices that `line_id` is **not** unique (that is a
finding, not a bug in your analysis); missing-value percentages match the dictionary; nothing was changed.

## 5. Output anatomy — the validation report

| Number you will see | Meaning | Good / suspicious |
| --- | --- | --- |
| Rows = 25,000 | Lines in the panel extract | Must match the generator summary exactly |
| Duplicated `line_id` = 150 | Same line loaded twice | Any value > 0 is suspicious: re-ingestion? |
| Return lines = 909 | Lines with `return_flag = True` | Plausible ~3–5% of lines in grocery (rule of thumb) |
| Negative quantity on non-return lines | Entry errors or mis-flagged returns | Should be 0 — investigate any |
| `household_size` missing 17.9% | Self-reported field | Ask *who* is missing (Day 1: MCAR/MAR/MNAR) |
| Default rate 4.0% | Share of accounts reaching 90+ DPD in 12 months | Plausible for a mixed card/loan book; check by vintage |
| Income missing 3.76% | Stated income absent | Low overall — but is it random? |

## 7. Exercises

=== "Basic → Advanced"

    1. Generate both datasets and paste the printed summary into your notes.
    2. How many duplicated `line_id` values are there in `transactions`? *(numeric)*
    3. What share of the bank's accounts defaulted within 12 months? *(numeric, %)*
    4. Ask for the grain of `performance_monthly` and test it (is `account_id` + `month_on_book` unique?).
    5. Find accounts with impossible ages. How many? *(numeric)*
    6. Write a five-bullet validation report for each dataset.

=== "Leader"

    1. Read a junior's validation report (use your own from the Basic → Advanced exercises or a peer's). Mark each of the seven checks as present / missing.

    3. Decide: which issues must be fixed before *any* analysis, and which can be handled lesson by lesson?
