## 2. Concept

=== "Basic → Advanced"

    ### 2.1 The arithmetic of many tests

    Each test at α = 0.05 has a 5% false-alarm rate. With m independent true-null tests, the chance of at least one false alarm is
    1 − 0.95^m: 23% for 5 tests, 64% for 20, 87% for 40.

    **Store screen.** We tested Fri–Sat vs Mon–Thu basket value separately in each of the 40 stores (median
    48 baskets per store). By chance we'd expect about 2.0 "significant" stores.

    | Method | Controls | Stores flagged |
    | --- | --- | --- |
    | None (raw p < 0.05) | nothing | 1 (store S034, p = 0.0456) |
    | Bonferroni (p < α/m) | chance of *any* false alarm (FWER) | 0 |
    | Holm (step-down Bonferroni) | FWER, more power | 0 |
    | Benjamini-Hochberg | expected share of false discoveries (FDR) | 0 |

    Store S034's weekend baskets are 11.85 higher on raw p = 0.0456; after
    Bonferroni its adjusted p is 1.0. Exactly what chance predicts — **targeting it would be chasing noise**
    (overall there is no weekend effect, L3.3).

    ### 2.2 Feature screens: FWER vs FDR

    We tested 30 candidate variables for association with default on a 3,000-account sample:
    19 real account variables and 11 columns of pure random noise.

    | Method | Real variables kept | Noise variables kept |
    | --- | --- | --- |
    | Raw p < 0.05 | 11 | **1** (smallest noise p = 0.0498) |
    | Bonferroni | 7 | 0 |
    | Holm | 7 | 0 |
    | **Benjamini-Hochberg (FDR 5%)** | **11** | 0 |

    Raw testing lets noise in; Bonferroni/Holm keep it out but discard real signals; **BH** keeps the real signals without admitting
    noise here. Rule of thumb: **Holm** when any false claim is costly (a regulatory or board claim, a single launch decision);
    **BH** for screening (features, segments, anomaly lists) where some false leads are acceptable and missed signals are costly.

    ### 2.3 The garden of forking paths

    p-hacking needs no bad intent — just flexibility. In the A/A store splits of L3.3, testing **one** pre-chosen category gave
    false positives 5.1% of the time. An analyst free to look at all 11 categories found at least one
    "winner" in **38.1%** of splits where nothing happened (theory for independent tests: 43.1%).

    | Fork | Example |
    | --- | --- |
    | many outcomes | units, revenue, margin, basket size… |
    | many subgroups | formats, regions, weekdays… |
    | flexible windows | weeks 70–77, or 70–75 "to avoid the holiday" |
    | outlier rules | trim, winsorise, or not |
    | optional stopping | check daily, stop when p < 0.05 |
    | HARKing | Hypothesising After the Results are Known |

    **Optional stopping.** Peeking at an A/A test 8 times and stopping at the first p < 0.05 gave a false-positive rate of
    **18.1%**, not 5%. Fix: a fixed horizon, or a sequential design with alpha spending (L4.2).

    ### 2.4 Prevention: pre-register

    One page before any data are touched: hypothesis, primary outcome, unit, window, exclusions, test, α, correction for secondary
    outcomes, sample size and stopping rule. Everything else is labelled **exploratory**.

=== "Leader"

    !!! abstract "Refresh"
        Many tests guarantee false positives. Control FWER (Holm) for confirmatory claims, FDR (BH) for screens. Forking paths and
        peeking inflate error rates without anyone cheating. Pre-registration is the cure.

    **Judgement points**

    - **Ask how many things were tried.** "We found the segment where the promo works" usually means "we tested 30 segments".
    - **Separate exploration from confirmation.** Exploratory findings earn a confirmatory test, not a rollout.
    - **Dashboards are multiple-testing machines.** A wall of 200 KPIs with red/green significance flags will light up ~10 by chance
      every week.
    - **Make pre-registration cheap** — a one-page template in the repo (`templates/preregistration.md`) and a rule that results without it
      are exploratory.

    !!! tip "Coaching card"
        Ask: *"What was the primary outcome, decided when, and how many other things did you look at?"*

## 5. Output anatomy — an adjusted p-value table

| Column | Read as |
| --- | --- |
| raw p | per-test surprise |
| Bonferroni p = min(1, m·p) | controls FWER; conservative |
| Holm p | controls FWER; uniformly more powerful than Bonferroni |
| BH q-value | expected false-discovery share among those kept |
| flagged (at 0.05) | per method — report which method was pre-chosen |

## 8. Exercises

### Retail · NorthStar

??? example "R3-14 · Basic · 40 store tests"
    **Business framing:** Marketing wants to target stores with a 'weekend basket effect'.

    **Deliverable:** Per-store Welch tests (Fri–Sat vs Mon–Thu basket); counts flagged raw, Bonferroni, Holm, BH.

    ??? success "Expected finding and model answer"
        **Expected:** 1 raw (store S034, p = 0.0456); Bonferroni 0; Holm 0; BH 0. Expected by chance: 2.0. *(tolerance: exact counts)*

        **Model answer:** Fewer raw hits than chance would produce; none survive correction. There is no evidence of store-specific weekend effects.

        **Common wrong answer:** Targeting store S034.

    **Leader drill:** Write the two-sentence reply to marketing.

??? example "R3-15 · Applied · Forking paths audit"
    **Business framing:** A promotion review reports a significant effect "in Express stores in the North on weekends, excluding the holiday week".

    **Deliverable:** List the forks taken; estimate how many analyses were implicitly possible; propose a pre-registration.

    ??? success "Expected finding and model answer"
        **Expected:** At least 4 forks (format, region, day type, window); with 3 formats × 4 regions × 2 day types × 2 windows = 48 possible cuts, a false positive is likely. *(tolerance: —)*

        **Model answer:** Treat it as exploratory. Pre-register a confirmatory test: primary outcome, population, window and analysis fixed in advance; secondary cuts corrected with Holm.

        **Common wrong answer:** Accepting the result because p < 0.05.

    **Leader drill:** How do you make pre-registration a habit rather than a bureaucratic burden?

### Finance · Meridian

??? example "F3-14 · Basic · A 30-feature screen"
    **Business framing:** A junior screens 30 features against default and keeps those with p < 0.05.

    **Deliverable:** Counts of real and noise features kept by raw, Bonferroni, Holm and BH (10 seeded noise columns as control).

    ??? success "Expected finding and model answer"
        **Expected:** Raw 11 real + 1 noise; Bonferroni 7 + 0; Holm 7 + 0; BH 11 + 0. *(tolerance: exact counts)*

        **Model answer:** Raw screening admits noise; Bonferroni/Holm drop real features; BH keeps the real ones without the noise. Use BH for screens, then validate on held-out data (Day 6).

        **Common wrong answer:** Feature selection on raw p-values.

    **Leader drill:** What is your team's standard for feature screening?

??? example "F3-15 · Applied · Peeking at a test"
    **Business framing:** The collections dashboard updates daily and the team will stop the test 'as soon as it's significant'.

    **Deliverable:** Simulate an A/A test with 8 interim looks; false-positive rate with peeking; propose a fix.

    ??? success "Expected finding and model answer"
        **Expected:** ≈ 18.1% false positives instead of 5%. *(tolerance: ± 2 pp)*

        **Model answer:** Every look is another chance for noise to cross 0.05. Use a fixed horizon, or a sequential design with alpha spending (O'Brien-Fleming) — L4.2.

        **Common wrong answer:** Stopping at the first p < 0.05.

    **Leader drill:** Draft the stopping rule for the next challenger.
