**Objectives** — you can: build features from raw tables (aggregates, ratios, lags, recency, flags for missingness); respect the
**observation point** so no feature uses information from after it; choose features with filter, wrapper and embedded methods; and
audit a feature list for leakage and provenance.

## 1. Business question

=== "Retail"

    > "Build customer-level features from transaction lines to predict who shops again."

=== "Finance"

    > "Do the first three months of account behaviour add to application data for predicting default?"

## 2. Concept

=== "Basic → Advanced"

    ### 2.1 The observation point

    Every feature must be computable **at the moment the prediction would be made**. Draw the timeline: feature window → observation
    point → outcome window. Anything from the outcome window is leakage.

    ### 2.2 Retail: a model that looks perfect

    Customers active in weeks 1–78 ({{ a.d6_r_customers | n }}); target = any purchase in weeks 79–104 ({{ a.d6_r_repeat_pct }}%).
    Features: baskets, log revenue, recency, promo share, number of categories, loyalty, tenure.

    | Features computed over | Test AUC |
    | --- | --- |
    | weeks 1–78 (correct) | **{{ a.d6_r_auc_logit }}** (gradient boosting {{ a.d6_r_auc_gbm }}) |
    | weeks 1–104 (includes the target window) | **{{ a.d6_r_auc_leaky }}** |

    The honest model has **no signal** — in this dataset, past shopping does not predict whether a customer returns in the next half
    year (top-decile repeat rate {{ a.d6_r_top_decile_rate }}% vs bottom {{ a.d6_r_bottom_decile_rate }}%). The leaky version is
    "perfect" because recency computed at week 104 tells you directly who shopped after week 78. A model can only find signal that
    exists; leakage manufactures it.

    ### 2.3 Finance: behavioural features that are legitimate

    Observation point = month 3 on book. From the monthly panel: max days past due, average utilisation and payment ÷ minimum due in
    months 1–3.

    | Feature set | Test AUC (gradient boosting) |
    | --- | --- |
    | application data ({{ a.d6_n_feat_app }} features) | {{ a.d6_models.gbm.auc }} |
    | + first-3-months behaviour | **{{ a.d6_beh_auc }}** (+{{ a.d6_beh_gain }}) |

    Accounts with any arrears in months 1–3 default at {{ a.d6_beh_dpd_default }}% vs {{ a.d6_beh_nodpd_default }}% for the rest.
    Behavioural scores (updated monthly) are standard in credit-card risk management for exactly this reason.

    ### 2.4 Feature families

    | Family | Examples |
    | --- | --- |
    | aggregates | count, sum, mean, max over a window (baskets, spend, DPD) |
    | ratios | payment ÷ minimum due, balance ÷ limit, promo share |
    | recency / frequency | weeks since last purchase, purchases per month |
    | lags and trends | utilisation 3 months ago, change in balance |
    | missingness flags | income missing (F02 — informative!) |
    | encodings | one-hot, target encoding (with out-of-fold fitting) |

    ### 2.5 Feature selection

    **Filter** (univariate tests, correlation, IV — with multiple-testing care, L3.7), **wrapper** (forward/backward selection on CV
    score), **embedded** (lasso, tree importance). Prefer embedded methods on cross-validated performance and keep the business-critical
    features explainable.

=== "Leader"

    !!! abstract "Refresh"
        Features decide model quality more than algorithms. Every feature needs a timestamp story: known at decision time, from a
        stable source, with a documented definition.

    **Judgement points**

    - **"Too good to be true" usually is.** An AUC of {{ a.d6_r_auc_leaky }} on customer behaviour should trigger a leakage audit,
      not a celebration.
    - **Feature provenance is a governance item.** Who owns the source, how often it refreshes, and whether it will exist in production.
    - **No signal is a valid finding.** Telling marketing that past purchases don't predict returns (in this data) saves a wasted
      targeting programme.

    !!! tip "Coaching card"
        Ask for the timeline drawing: feature window, observation point, outcome window — for every feature in the list.

| --- | --- |
| name | `max_dpd_3` |
| definition | max days past due, months on book 1–3 |
| window vs observation point | months 1–3; observation at month 3 |
| source and owner | `performance_monthly`, collections data team |
| missing handling | 0 if no record (new account) + indicator |
| leakage check | passed — no outcome-window data |

## 6. Scenario matrix

=== "Basic → Advanced"

    | Situation | Approach |
    | --- | --- |
    | event-level data, entity-level prediction | aggregate over a window ending at the observation point |
    | missingness carries information | add an indicator, don't just impute |
    | high-cardinality category | target encoding with out-of-fold fitting |
    | many candidate features | embedded selection on CV score |

=== "Leader"

    | Claim | Question | Norm |
    | --- | --- | --- |
    | "AUC 0.99 on customer data" | which window built the features? | leakage audit |
    | "500 features" | provenance, stability, cost? | feature catalogue |
    | "past behaviour doesn't predict" | properly tested? | accept valid nulls |
