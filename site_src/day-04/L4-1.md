**Objectives** — you can: design a test (unit of randomisation, primary / secondary / guardrail metrics, duration, sample size);
check sample-ratio mismatch (SRM) before reading any result and localise its cause; recognise novelty, primacy and interference;
and decide when a test result can be trusted at all.

## 1. Business question

=== "Retail"

    > "Did the new e-coupon raise 14-day conversion in the app?"

=== "Finance"

    > "Design the test for a new credit-card balance-transfer offer."

## 2. Concept

=== "Basic → Advanced"

    ### 2.1 The design checklist

    | Decision | E-coupon (retail) | Card offer (finance) |
    | --- | --- | --- |
    | Unit of randomisation | app user | customer (not account — one customer, one offer) |
    | Primary metric | converted within 14 days | offer take-up within 30 days |
    | Secondary | revenue in 14 days | balance transferred |
    | Guardrails | revenue must not fall | 90-day delinquency, complaints, margin |
    | Planned split | 50/50 | 50/50, stratified by risk band |
    | Sample size | from `rcp_power` (L3.6) | +1 pp on a 6% base: **{{ a.d4_card_n_per_arm | n }} per arm** |
    | Duration | ≥ 2 full weeks (weekly cycles) | ≥ one statement cycle + 30 days |
    | Analysis plan | pre-registered (L3.7) | pre-registered |

    ### 2.2 Hygiene check 1 — sample-ratio mismatch

    The test was planned 50/50. Logged: **{{ a.d4_ab_nt | n }} treatment vs {{ a.d4_ab_nc | n }} control** ({{ a.d4_ab_share_t }}% treatment).
    A chi-square test against 50/50 gives χ² = {{ a.d4_srm_chi2 }}, **p = {{ a.d4_srm_p }}**. With true 50/50 randomisation a gap
    this large essentially never happens. Something removed or added users non-randomly — **stop and diagnose before reading the
    effect**.

    **Localise it.** Repeat the check within segments:

    | Segment | Treatment | Control | p |
    | --- | --- | --- | --- |
    {% for v, r in a.d4_srm_by_version.items() %}| app {{ v }} | {{ r.t | n }} | {{ r.c | n }} | {{ r.p }} |
    {% endfor %}| platform android / ios | — | — | {{ a.d4_srm_by_platform.android }} / {{ a.d4_srm_by_platform.ios }} |

    The mismatch lives in **app version 3.2** (both platforms are affected only because 3.2 runs on both). In 3.2 the control arm
    shows {{ a.d4_v32_conv_c }}% conversion against {{ a.d4_v32_conv_t }}% for treatment — control users who *did not* convert went
    missing from the log on that version, inflating control's conversion.

    ### 2.3 What the broken test says — and what it hides

    | Reading | Treatment | Control | Lift | 95% CI | p |
    | --- | --- | --- | --- | --- | --- |
    | As logged (SRM) | {{ a.d4_naive_t }}% | {{ a.d4_naive_c }}% | {{ a.d4_naive_lift_pp }} pp | {{ a.d4_naive_ci[0] }} to {{ a.d4_naive_ci[1] }} | {{ a.d4_naive_p }} |
    | Excluding app 3.2 (SRM gone, p = {{ a.d4_clean_srm_p }}) | {{ a.d4_clean_t }}% | {{ a.d4_clean_c }}% | **{{ a.d4_clean_lift_pp }} pp** | {{ a.d4_clean_ci[0] }} to {{ a.d4_clean_ci[1] }} | {{ a.d4_clean_p }} |

    The logging bug hid a real lift (the planted true effect is +{{ a.d4_true_lift_pp }} pp — inside the clean CI). Excluding 3.2 is a
    **sensitivity analysis**: it assumes 3.2 users respond like the others. The proper fix is to repair logging and re-run (or recover
    the missing users from the assignment service).

    ### 2.4 Hygiene check 2 — balance and A/A

    Pre-period 30-day spend does not differ by arm in the clean data (p = {{ a.d4_pre_balance_p }}). Platforms should run regular A/A
    tests (L3.3): ~5% "significant", SRM rarely.

    ### 2.5 Threats that a clean SRM does not rule out

    | Threat | What happens | Defence |
    | --- | --- | --- |
    | Novelty effect | users try the new thing, then revert | run ≥ 2 weeks; plot effect by week of exposure |
    | Primacy effect | users resist change at first | same |
    | Interference | treated users affect control (shared stock, social, marketplace) | cluster randomisation (stores, regions) |
    | Contamination | control users see the offer (shared devices, staff) | assign at the right level; measure exposure |
    | Seasonality | test window unrepresentative | avoid holidays or include full cycles |

=== "Leader"

    !!! abstract "Refresh"
        Design before data: unit, metrics, guardrails, size, duration, analysis plan. Read nothing until the SRM check passes.
        An SRM means a broken experiment, not an interesting result.

    **Judgement points**

    - **Make SRM a hard gate.** The e-coupon readout as logged said "no effect" (p = {{ a.d4_naive_p }}); the real effect was about
      +{{ a.d4_clean_lift_pp }} pp. A broken pipeline almost killed a winning idea.
    - **Guardrails are the leader's metrics.** Juniors optimise the primary metric; you protect margin, risk and customers.
    - **The unit of randomisation is a business decision.** Store-level tests avoid interference but have few units (L3.6); user-level
      tests have power but may contaminate.

    !!! tip "Coaching card"
        First question on any readout: *"What was the planned split and what did we observe?"* Second: *"Which guardrails moved?"*

## 6. Scenario matrix

=== "Basic → Advanced"

    | Check | Fails → |
    | --- | --- |
    | SRM overall | stop; localise by segment, date, platform |
    | SRM only in one segment | logging/eligibility bug there; sensitivity analysis + fix |
    | Pre-period imbalance (p small) | check randomisation; use CUPED/ANCOVA |
    | Effect fades week by week | novelty; extend the test |
    | Control exposed to treatment | contamination; re-design unit |

=== "Leader"

    | Readout says | You say | Norm |
    | --- | --- | --- |
    | "52.5/47.5 is close enough to 50/50" | "p = {{ a.d4_srm_p }} — it's broken" | SRM gate at p < 0.001 |
    | "primary up, complaints up" | guardrail breach → don't ship | guardrails pre-agreed |
    | "ran 4 days, significant" | weekly cycle, novelty | ≥ 2 full weeks |
