## 2. Concept

=== "Basic → Advanced"

    ### 2.1 The arithmetic of many tests

    Each test at α = 0.05 has a 5% false-alarm rate. With m independent true-null tests, the chance of at least one false alarm is
    1 − 0.95^m: 23% for 5 tests, 64% for 20, 87% for 40.

    **Store screen.** We tested Fri–Sat vs Mon–Thu basket value separately in each of the {{ a.d3_mt_r_tests }} stores (median
    {{ a.d3_mt_r_median_n }} baskets per store). By chance we'd expect about {{ a.d3_mt_r_expected_fp }} "significant" stores.

    | Method | Controls | Stores flagged |
    | --- | --- | --- |
    | None (raw p < 0.05) | nothing | {{ a.d3_mt_r_raw }} (store {{ a.d3_mt_r_min_store }}, p = {{ a.d3_mt_r_min_p }}) |
    | Bonferroni (p < α/m) | chance of *any* false alarm (FWER) | {{ a.d3_mt_r_bonf }} |
    | Holm (step-down Bonferroni) | FWER, more power | {{ a.d3_mt_r_holm }} |
    | Benjamini-Hochberg | expected share of false discoveries (FDR) | {{ a.d3_mt_r_bh }} |

    Store {{ a.d3_mt_r_min_store }}'s weekend baskets are {{ a.d3_mt_r_min_diff }} higher on raw p = {{ a.d3_mt_r_min_p }}; after
    Bonferroni its adjusted p is {{ a.d3_mt_r_min_padj_bonf }}. Exactly what chance predicts — **targeting it would be chasing noise**
    (overall there is no weekend effect, L3.3).

    ### 2.2 Feature screens: FWER vs FDR

    We tested {{ a.d3_mt_f_tests }} candidate variables for association with default on a {{ a.d3_mt_f_n | n }}-account sample:
    {{ a.d3_mt_f_real }} real account variables and {{ a.d3_mt_f_tests - a.d3_mt_f_real }} columns of pure random noise.

    | Method | Real variables kept | Noise variables kept |
    | --- | --- | --- |
    | Raw p < 0.05 | {{ a.d3_mt_f_raw_real }} | **{{ a.d3_mt_f_raw_noise }}** (smallest noise p = {{ a.d3_mt_f_noise_min_p }}) |
    | Bonferroni | {{ a.d3_mt_f_bonf_real }} | {{ a.d3_mt_f_bonf_noise }} |
    | Holm | {{ a.d3_mt_f_holm_real }} | {{ a.d3_mt_f_holm_noise }} |
    | **Benjamini-Hochberg (FDR 5%)** | **{{ a.d3_mt_f_bh_real }}** | {{ a.d3_mt_f_bh_noise }} |

    Raw testing lets noise in; Bonferroni/Holm keep it out but discard real signals; **BH** keeps the real signals without admitting
    noise here. Rule of thumb: **Holm** when any false claim is costly (a regulatory or board claim, a single launch decision);
    **BH** for screening (features, segments, anomaly lists) where some false leads are acceptable and missed signals are costly.

    ### 2.3 The garden of forking paths

    p-hacking needs no bad intent — just flexibility. In the A/A store splits of L3.3, testing **one** pre-chosen category gave
    false positives {{ a.d3_aa_fpr }}% of the time. An analyst free to look at all {{ a.d3_n_cats_aa }} categories found at least one
    "winner" in **{{ a.d3_fork_any }}%** of splits where nothing happened (theory for independent tests: {{ a.d3_aa_any_theory }}%).

    | Fork | Example |
    | --- | --- |
    | many outcomes | units, revenue, margin, basket size… |
    | many subgroups | formats, regions, weekdays… |
    | flexible windows | weeks 70–77, or 70–75 "to avoid the holiday" |
    | outlier rules | trim, winsorise, or not |
    | optional stopping | check daily, stop when p < 0.05 |
    | HARKing | Hypothesising After the Results are Known |

    **Optional stopping.** Peeking at an A/A test 8 times and stopping at the first p < 0.05 gave a false-positive rate of
    **{{ a.d3_peek_fpr }}%**, not 5%. Fix: a fixed horizon, or a sequential design with alpha spending (L4.2).

    ### 2.4 Prevention: pre-register

    One page before any data are touched: hypothesis, primary outcome, unit, window, exclusions, test, α, correction for secondary
    outcomes, sample size and stopping rule. Everything else is labelled **exploratory**.

=== "Leader"

    !!! abstract "Refresh"
        Many tests guarantee false positives. Control FWER (Holm) for confirmatory claims, FDR (BH) for screens. Forking paths and
        peeking inflate error rates without anyone cheating. Pre-registration is the cure.

    **Judgement points**

    - **Ask how many things were tried.** "We found the segment where the promo works" usually means "we tested 30 segments".
    - **Separate exploration from confirmation.** Exploratory findings earn a confirmatory test, not a rollout.
    - **Dashboards are multiple-testing machines.** A wall of 200 KPIs with red/green significance flags will light up ~10 by chance
      every week.
    - **Make pre-registration cheap** — a one-page template in the repo (`templates/preregistration.md`) and a rule that results without it
      are exploratory.

    !!! tip "Coaching card"
        Ask: *"What was the primary outcome, decided when, and how many other things did you look at?"*

## 5. Output anatomy — an adjusted p-value table

| Column | Read as |
| --- | --- |
| raw p | per-test surprise |
| Bonferroni p = min(1, m·p) | controls FWER; conservative |
| Holm p | controls FWER; uniformly more powerful than Bonferroni |
| BH q-value | expected false-discovery share among those kept |
| flagged (at 0.05) | per method — report which method was pre-chosen |

=== "Basic → Advanced"

    | Situation | Correction |
    | --- | --- |

    | a few secondary outcomes | Holm |
